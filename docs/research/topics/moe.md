# MoE

MLP を複数の専門家（expert）に分け、トークンごとに一部だけを動かす。計算を増やさずにパラメータを増やせる。v7 で採用すると決めた（2026-11-05）。

## 他の人の結果

- **規模と効率：** [Ling の効率の規模則](../sources/moe-efficiency-leverage.md)は、試した全ての大きさで MoE が計算あたり効率的で、使う割合が小さいほど、計算が大きいほど得になるとした。細かさは12前後が最良で、共有の専門家は 1e20 FLOPs 以下で 16.7%。[細かい MoE の規模則](../sources/fine-grained-moe-scaling.md)も、差は規模とともに広がるとした。[同じ資源での比較](../sources/moe-equal-resources.md)は、2B と 7B で、全体・計算・データをそろえても、使う割合が最適な範囲なら MoE が勝つとした。[DeepSeekMoE](../sources/deepseekmoe.md) は 2B で、1.5倍の計算の GShard に並んだ。[OLMoE](../sources/olmoe.md) は 7B のうち 1B を使い、router の z-loss を使う。
- **小さな規模：** [2500万以下の比較](../sources/tiny-moe.md)では、使う大きさをそろえると MoE が勝ち、全体の大きさをそろえると負けた。[3500万の比較](../sources/moe-below-measurement-floor.md)は、1000万トークンでは課題が当てずっぽうの水準で、差を測れなかった。
- **時間：** [nanochat の LOG](../sources/nanochat-log.md)（2026-02-19）は、ステップあたりの検証損失は良くなったが、d18 で MFU が約46%から約35%に落ち、時間で負けとした。課題の点では比べていない。
- **知識と推論：** [Mixture of Parrots](../sources/mixture-of-parrots.md) と[推論と疎さの研究](../sources/moe-sparsity-reasoning.md)は、専門家を増やすと知識と記憶は上がり、推論は使う計算とトークン数で決まるとした。
- **負荷の均し方：** [補助の損失を使わない均し方](../sources/loss-free-balancing.md)（DeepSeek-V3 の形。softmax では偏りを差の大きさで動かした）、[更新全体で均す損失](../sources/global-batch-balancing.md)（専門家が分野ごとに分かれ、点も上がる）。[DeepSeek-V3](../sources/deepseek-v3.md) の比較では、更新全体で均す補助の損失は 1B と 3B で偏りと同じ検証損失だった。[OLMoE](../sources/olmoe.md) は均しの損失をなくすと最初の層で専門家が偏った。[Mellum2](../sources/mellum2.md) も更新全体で均す。
- **重みを保つ学習での MoE：** [HyperP](../sources/hyperp.md) は、重みを初めのノルムに保つ MuonH で、選んだ専門家を点数の平方根で混ぜると（SqrtGate）全ての細かさで損失が下がり、細かくするほど良くなり続けた。router の点の伸びも抑えた。均しの損失は層ごとに 0.1 が、0.01 や 0.001 より損失も均し方も良かった。全体を能動の何倍にするかでも、倍にするごとに損失が下がった。
- **メモリ：** [SonicMoE](../sources/sonicmoe.md) は、逆伝播に入力と最初の積だけを保存し、専門家に配ったコピーと出力を保存しないことで、活性化のメモリを45%減らした。
- **密なモデルから作る：** [Drop-Upcycling](../sources/drop-upcycling.md)、[作り替えの規模則](../sources/upcycling-scaling-laws.md)。
- **専門家の FP8：** [PyTorch の MXFP8](../sources/mxfp8-moe-torchao.md) は、データセンター向けの Blackwell で学習全体が1.3倍。RTX 5090 では使えない。

## 私たちの測定

[v7 の速さ](../experiments/v7-throughput.md)。RTX 5090 で、1トークンに使う単位を密な形と同じ 4,096 にした MoE（専門家 1024×12 から3つと共有の専門家1つ、全体約11億）は、1窓ずつで毎秒約 38,300 トークン、メモリ 26.0GiB。同じ機械の密なモデル（2窓ずつ、58,400）より34%遅い。GPU が計算していた割合は91%で、遅さの主な原因は専門家の計算そのもの（bf16 で、PyTorch のまとめた積が専門家ごとの積に分かれる）。コンパイルの自動調整では、専門家の積だけなら29%速くなった。コンパイルした逆伝播が配ったトークンのコピーを保存していて、細かい専門家ほどメモリが足りなかった（直した）。直したあとも、細かい 256×48（13を使う）は 1024×12 より30%遅く、トークンのコピーを集める処理が GPU の時間の約10%を占めた。HyperP の表では、細かさを4から16にしても損失は0.015しか下がらないので、この GPU では粗い専門家のほうが得とみた。

DeepSeek-V3 の偏りで均すと、120回の更新のうちに全トークンが同じ専門家を選ぶ状態になった。手元の小さな MoE で、全トークンが同じ専門家を好む状態から始めると、偏りは働くが、全トークンがそろって次の専門家に移るだけで均等にならなかった。トークンごとの好みが十分ばらけていない学習の初めには、偏りだけでは均せない。更新全体で数える均しの損失（0.01）に替え、点数そのもので混ぜたときも、120回の更新で全トークンが同じ1つの専門家を選ぶ状態になった。HyperP の分析では、点数そのもので混ぜると選んだ専門家の出力は1つに集まったときだけ大きく、重みの大きさを保つ学習ではこれが集まる方へ引く。

## コード

`pretrain/model.py` の `Experts`：OLMoE の形（float32 の router、z-loss 0.001）に、二乗 ReLU の専門家と共有の専門家を足した。負荷は更新全体で数える均しの損失（層ごとに 0.1）で均す。選んだ専門家は点数の平方根で混ぜ、共有の専門家と √0.5 ずつで足す。各専門家の出力の行列は、単位が少ない分だけ大きく始め、出力の大きさを密な網にそろえる。Hyperball は専門家の行列と router にも使える。逆伝播には単語と最初の積だけを保存する（`ExpertProducts`）。Hugging Face 形式への書き出しにも対応した。
