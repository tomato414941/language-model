# v7 の速さとメモリ（RTX 5090）

2026-11-05 に、v7 の候補の形を Vast の RTX 5090（32GB）1台で測った（`runs/profile-v7`、`runs/profile-v7-moe`）。どれもコンパイルあり、Hyperball（倍率10）、出力の行列は乱数から始める。データは合成で、文書は Web の平均と同じ約1,325トークンで区切り、各文書は Zipf 分布の語の一節を繰り返す。速さは1更新16窓の測定から、1更新128窓（v7 の 100万トークン）に直した値。データの読み込み、重みの保存、検証は含まない。

## 文書ごとの注意

PyTorch の varlen の注意（FlashAttention-2）を、文書の境界を2のべき乗の数にそろえた形とそろえない形で、コンパイルあり・なしの両方で float32 の計算と比べた。12回ずつ試し、非有限の値はなく、出力と勾配の相対誤差は 0.4〜0.6% だった。v6 の測定でコンパイル後に NaN が出たのは、2回とも同じ1台の機械だった。

## 普通のモデル

| 形 | 精度 | 毎秒のトークン | メモリ |
|---|---|---|---|
| 約3.9億（幅1024、32層） | bf16 | 48,500 | 17.5GiB |
| 約3.9億 | FP8（注意の入力は bf16、テンソルごとのスケール） | 59,400 | 13.9GiB |
| 約3.9億 | FP8（行ごとのスケール） | 50,300 | 13.9GiB |
| 約7.2億（幅1280、40層） | bf16 | 28,900 | 27.7GiB |
| 約7.2億 | FP8 | 36,000 | 21.9GiB |

FP8 の4通りは、合成データで250回の更新を続けても非有限の値が出なかった。GPU の時間の内訳は、約3.9億の bf16 で行列の計算62%、注意18%、行列以外の細かい計算18%。

別の機械で、約3.9億の FP8 の学習の進め方を比べた。

| 進め方 | 毎秒のトークン | メモリ |
|---|---|---|
| 1窓ずつ、窓ごとに損失を取り出す | 57,600 | 13.9GiB |
| 1窓ずつ、損失を更新ごとにまとめて取り出す | 58,300 | 13.9GiB |
| 2窓ずつ、損失をまとめて取り出す | 62,600 | 21.1GiB |

## MoE

1トークンに使う単位は、共有の専門家と選んだ専門家で密な形と同じ 4,096 にした。専門家の大きさ×数で書く。

- 1回目と2回目：負荷は DeepSeek-V3 の偏りで均した。二乗 ReLU の値が自動の精度切り替えで float32 になり、bf16 の専門家の行列との積で止まった。コードを直した。専門家 512×24（7つを使う）と 256×48（14を使う）は、1窓ずつでも 32GB に収まらなかった。1024×12（3つを使う）は、1窓ずつで 30.4GiB、毎秒 37,200 トークン。同じ機械の普通のモデル（2窓ずつ）の 64,100 より42%遅い。偏りを動かす速さ 0.001 では、120回の更新で全トークンが同じ専門家を選ぶようになった。専門家の行列の FP8 は、PyTorch が計算能力 12.0 に対応していなかった。bf16 の専門家の計算は 159 TFLOP/s だった。
- 3回目：専門家ごとのトークン数を同期なしで数える形（scatter-add）に直し、偏りを動かす速さを 0.01 にした。1024×12 は、1窓ずつで毎秒 38,200 トークン、27.5GiB。同じ機械の普通のモデル（1窓ずつ）の 58,200 より34%遅い。偏りは変わらず、全トークンが同じ専門家を選ぶ状態になった。専門家を 1024×8 に減らしても、2窓ずつは 32GB に収まらなかった。コンパイルを含む準備は、普通のモデルの約5.5分に対して約7分だった。
- 4回目：負荷を更新全体で数える均しの損失（0.01）で均し、逆伝播には単語と最初の積だけを残すつもりにした。普通のモデル（2窓ずつ）は毎秒 58,400 トークン、21.1GiB。1024×12 は2窓ずつでは収まらず、1窓ずつで毎秒 38,300 トークン、26.0GiB。最後の10回の更新で、一番使われた専門家が均等な割合の4.0倍、つまり全トークンに選ばれていた。コンパイルの自動調整（`max_autotune_gemm`）では専門家の積が Triton のまとめた積になり、38,800 トークン（+1.5%）。256×48 は1窓ずつでも収まらなかった。専門家の積だけを測ると（256×48、2窓分）、PyTorch の積が 140 TFLOP/s、自動調整が 180 TFLOP/s。torchao の FP8 のまとめた積は動かなかった（`pad_token_groups_for_grouped_mm` が未対応）。
- GPU が計算していた割合：2回目と3回目に「時間の53%・51%」とみたのは、プロファイラーで遅くなった時間で割った誤りだった（普通のモデルの進め方の比較で書いた 69〜81% も同じ誤りで、表から除いた）。4回目にプロファイラーなしの時間で割ると、1024×12 は91%、普通のモデルは95%。MoE の遅さの主な原因は専門家の計算そのもので、普通のモデルの MLP は FP8 で掛けるが、専門家は bf16 で掛ける。PyTorch のまとめた積は、計算能力 12.0 では専門家ごとの積に分かれ、呼ぶたびに専門家の大きさを GPU から読み戻して待つ（ソースで確かめた）。
- 4回目のあと、手元の CPU で、コンパイルした逆伝播が保存するものを調べた。PyTorch のコンパイラーが逆伝播の集め直しと前向きの集めを1つにまとめ、配ったトークンのコピー（使う専門家の数に比例する）と、上向きの行列の bf16 のコピーを保存していた。256×48 ではコピーだけで1窓あたり約7GB になる。逆伝播でコピーを勾配と一緒に集めるように直し、保存されなくなったことを確かめた。
- 5回目：HyperP の混ぜ方（点数の平方根、共有の専門家と √0.5 ずつ、層ごとの均しの損失 0.1、router も Hyperball）にし、コピーを保存しないコードで測った。普通のモデル（2窓ずつ）は毎秒 58,600 トークン。256×48 は2窓ずつでは収まらず、1窓ずつで毎秒 26,900 トークン、26.4GiB で、1024×12 より30%遅い。トークンのコピーを集める処理だけで GPU の時間の約10%を使った。自動調整は、集め直しを Triton の積に取り込むところでコンパイルに失敗した。256×80（1窓ずつ）と 1024×12（2窓ずつ）は収まらなかった。最後の10回の更新で、ある層では一番使われた専門家が均等な割合の3.7倍、つまり全トークンに選ばれていた。どの測定も、学習は1更新16,000トークン、学習率 0.0032（v7 の1.6倍）で、本番の学習とは違う。

## 借りた機械

1回目の機械は、準備のダウンロードが止まった（28分で26/64のパッケージ）。SSH の鍵のファイルの持ち主か権限が sshd に拒まれる機械（「bad ownership or modes for file /root/.ssh/authorized_keys」）に2回当たった。コンテナの起動時に権限を直す処理を足すと、それ以降はつながった。
